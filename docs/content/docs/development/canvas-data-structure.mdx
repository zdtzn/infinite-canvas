# 画布数据结构

当前项目同时支持正式服务端模式和本地前端开发模式。两者使用同一套前端数据结构，但持久化位置不同。

## 正式服务端模式

Docker 构建后的应用由 Bun 单体服务提供，服务端是权威数据源：

| 位置                   | 内容                                                 |
| ---------------------- | ---------------------------------------------------- |
| `/data/app.sqlite`     | 用户、渠道、项目、任务、生成历史、修炼配置和审计数据 |
| `/data/assets`         | 按用户保存的藏卷阁文件与头像                         |
| `/data/job-files`      | 生图任务结果                                         |
| `/data/job-references` | 生图任务参考文件                                     |
| `/data/prompt-cache`   | 受控提示词图片缓存                                   |
| `/data/backups`        | SQLite 一致性快照                                    |

所有项目、素材、历史和任务查询都以当前登录会话的用户 ID 为边界。文件通过鉴权 API 读取，`storageKey` 不是可公开访问的文件 URL。

前端仍会保留按用户分区的浏览器缓存，用于页面补水、生成历史合并和迁移旧数据；登录切换时会校验缓存归属，服务端记录优先于过期本地副本。

## 本地前端模式

直接运行 `web/bun run dev` 时不启用正式服务端能力，数据保存在浏览器 `localForage`：

- 画布项目与应用状态：数据库 `infinite-canvas`，store `app_state`。
- 图片 Blob：store `image_files`。
- 视频和音频 Blob：store `media_files`。
- 生成历史与偏好：按本地用户键分区保存。

该模式适合前端调试或个人可信环境，不应被当作多人公网部署方案。

## 项目结构

每个画布项目的核心结构为：

```ts
type CanvasProject = {
  id: string;
  title: string;
  createdAt: string;
  updatedAt: string;
  nodes: CanvasNodeData[];
  connections: CanvasConnection[];
  chatSessions: CanvasAssistantSession[];
  activeChatId: string | null;
  backgroundMode: "lines" | "dots" | "blank";
  viewport: { x: number; y: number; k: number };
};
```

服务端保存项目 JSON、更新时间和版本信息。前端保存前会进行结构校验；同一账号多标签页编辑时使用单写锁，服务端版本冲突不会被静默覆盖。

## 节点与连线

```ts
type CanvasNodeData = {
  id: string;
  type: "image" | "text" | "config" | "video" | "audio" | string;
  title: string;
  position: { x: number; y: number };
  width: number;
  height: number;
  metadata?: CanvasNodeMetadata;
};

type CanvasConnection = {
  id: string;
  fromNodeId: string;
  toNodeId: string;
};
```

节点 `metadata` 保存文本、提示词、生成模式、模型、比例、状态、媒体尺寸和 `storageKey` 等业务数据。插件节点可扩展 `type` 与 metadata，但必须遵守插件 SDK 的序列化约定。

连线只保存起点和终点节点 ID。删除节点时会同步清理相关连线；图片组根节点还会维护子节点和主图关系。

## 媒体文件

画布 JSON 不长期内嵌大体积 base64 文件。图片、视频和音频节点保存：

- `storageKey`：持久文件标识。
- `content`：当前会话可展示的 URL。
- `mimeType`、`bytes`、自然宽高等元信息。

正式模式下 `content` 通常解析为同源鉴权 API；本地模式下通常解析为 `blob:` URL。发送到只接受 base64 的上游接口时，前端或服务端会在请求阶段临时转换，不把 base64 当作长期项目存储格式。

## 旧数据迁移

- SQLite 启动时执行版本化迁移。
- 发现旧 `state.json` 时会导入现有用户、渠道、项目、任务和素材引用，成功后由 SQLite 接管。
- 浏览器旧项目中的 `data:image/*` 会在补水时转换为独立文件并补充 `storageKey`。
- 生成历史和藏卷阁同步会保留用户归属，避免把旧缓存合并到错误账号。

迁移完成后仍应保留部署前备份，直到登录、项目、藏卷阁和生成历史抽查通过。

## 清理与备份

- 服务端按配置清理过期终态任务、任务文件、媒体任务和提示词缓存。
- 删除项目或素材时只清理当前用户拥有且不再被引用的文件。
- SQLite 自动快照不包含全部媒体文件；完整恢复必须使用 `ops/backup-volume.sh` 创建的数据卷归档。
- WebDAV 可同步画布、素材和历史副本，但不会同步平台渠道 API Key，也不能替代 `/data` 数据卷备份。
